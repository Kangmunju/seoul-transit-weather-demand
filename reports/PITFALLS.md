# 프로젝트 주요 함정과 주의사항

## 1. 문서 목적

서울 지하철 수요와 날씨 예측 프로젝트를 진행하면서
직접 확인한 주요 함정과 주의사항을 정리.

코드가 정상적으로 실행되거나
모델의 점수가 높게 나오는 것만으로
분석이 올바르다고 판단할 수 없음.

데이터의 의미, 전처리 방식, 시간 순서,
평가 방법, 외부 환경 변화에 따라
결과가 크게 달라질 수 있음을 확인함.


## 2. 역명 표기를 그대로 사용하면 같은 역이 분리될 수 있음

원본 데이터에는 역명 뒤에
괄호 형태의 부기명이 붙은 경우가 존재.

예를 들면 다음과 같은 형태.

```text
강변(동서울터미널)
경복궁(정부서울청사)
광화문(세종문화회관)
```

원본 데이터의 고유 역명은 545개였지만
부기명을 제거한 뒤에는 540개로 감소.

따라서 역명을 그대로 사용하면
실제로는 같은 역을 서로 다른 역으로
집계할 가능성이 있음.

### 대응

역명 뒤의 괄호 형태 부기명을 제거하고
표준화한 역명을 사용.


## 3. 이상값이 있다고 행 전체를 삭제하면 안 됨

원본 지하철 데이터에서
`total <= 0`인 행을 확인.

이 값을 처리하기 위해 행 전체를 삭제하면
같은 날짜와 역에 포함된
다른 정상 정보까지 잃을 수 있음.

### 대응

문제가 있는 `total` 값만 결측 처리하고
나머지 정보는 유지.

이상값이 발견됐다고 무조건 행을 삭제하지 말고
데이터 구조를 먼저 확인해야 함.


## 4. 총강수량을 그대로 비로 해석하면 안 됨

날씨 데이터에는 다음 변수가 존재.

```text
precip_mm = 총강수량
rain_mm   = 강우량
```

실제 원본 데이터를 확인했을 때
`precip_mm != rain_mm`인 날짜가 존재함.

총강수량에는 눈과 같은 형태의 강수도
포함될 수 있기 때문.

### 대응

비가 지하철 이용량에 미치는 영향을 분석할 때는
`precip_mm`이 아닌 실제 강우량인
`rain_mm`을 사용.

변수명만 보고 의미를 판단하지 말고
실제 데이터 정의를 확인해야 함!


## 5. 비 오는 날과 맑은 날의 평균만 비교하면 안 됨

비가 오는 날의 이용량과
비가 오지 않는 날의 이용량을
단순 평균으로 비교하면
비의 효과처럼 보이는 차이가 나타날 수 있음.

하지만 지하철 이용량은
평일과 주말 자체의 차이가 큼.

따라서 비가 특정 요일에 더 많이 포함되어 있다면
요일 효과가 비의 효과처럼 보일 수도 있음.

### 대응

평일과 주말 등
수요에 영향을 주는 조건을 함께 고려하여
강우 효과를 비교.

단순한 두 집단의 평균 차이를
바로 비의 효과라고 해석하면 안 됨.


## 6. 시계열 데이터를 무작위로 섞으면 미래 정보가 섞일 수 있음

지하철 수요는 시간 순서가 존재하는 데이터.

전체 데이터를 무작위로 섞은 뒤
학습과 테스트 데이터로 나누면

미래 시점과 가까운 데이터가
학습 데이터에 포함될 수 있음.

이 경우 실제 미래를 예측하는 상황보다
문제가 쉬워지면서
모델 성능이 과대평가될 가능성이 있음.

### 대응

시간 순서를 유지한 분할을 사용하고
walk-forward 검증도 함께 수행.

```text
과거 데이터 → 학습
그다음 기간 → 평가
```

실제 미래 예측과 비슷한 조건에서
모델을 평가해야 함.


## 7. lag와 rolling 특징도 누수를 만들 수 있음

과거 이용량을 사용하는
lag와 rolling 특징은
시계열 수요 예측에서 중요한 특징.

하지만 특징을 만드는 과정에서
현재 또는 미래의 정답 정보가 들어가면
데이터 누수가 발생함.

예를 들어 현재 날짜의 이용량이 포함된
rolling 평균을 사용하여
현재 날짜의 이용량을 예측하면 안 됨.

### 대응

예측 시점보다 이전에
실제로 알 수 있었던 값만 사용.

특징을 만들 때는 항상

```text
이 값을 실제 예측 시점에 알고 있었는가?
```

를 확인해야 함.

예측 당시 알 수 없는 값이라면
모델 입력 특징으로 사용하면 안 됨!


## 8. Random split의 높은 점수를 그대로 믿으면 안 됨

무작위 분할에서 높은 성능이 나왔다고 해서
실제 미래 수요도 같은 수준으로
예측할 수 있다고 판단하면 안 됨.

시계열에서는 가까운 날짜끼리
수요 패턴이 비슷하기 때문에
무작위 분할이 문제를 쉽게 만들 수 있음.

### 대응

random split 결과만으로 판단하지 않고
시간순 분할과 walk-forward 검증 결과를
함께 확인.

포트폴리오에서도
가장 높은 점수 하나만 제시하기보다
평가 방법에 따른 차이를 설명해야 함.


## 9. 전체 평균 성능만 보면 특정 시기의 실패를 놓칠 수 있음

여러 기간의 결과를
하나의 평균 점수로 합치면

특정 기간에서 모델이 크게 실패한 사실이
가려질 수 있음.

실제 walk-forward 검증에서도
2019년으로 학습하고
2020년을 예측하는 구간에서
성능이 크게 저하되는 것을 확인.

### 대응

전체 평균뿐 아니라
fold별 성능도 함께 확인.

```text
전체 성능
+
시점별 성능
```

특정 시점에서 성능이 무너졌다면
모델 자체의 문제만 볼 것이 아니라
그 시기의 데이터 구조가 변했는지도 확인해야 함.


## 10. 팬데믹은 단순한 이상치가 아님

2020년 지하철 일평균 이용량은
2019년 대비 약 27.7% 감소.

이 변화를 단순 이상치로 처리하면
실제 사회적 변화로 발생한
수요 구조 변화 자체를 제거하게 됨.

팬데믹은 개별 데이터의 오류가 아니라
데이터가 만들어지는 환경 자체가
달라진 사건이라고 판단.

### 대응

팬데믹 이전, 급성기, 회복기,
엔데믹 이후를 구분하여 분석.

모델에서도 팬데믹 국면 정보를
특징으로 사용할 수 있도록 구성.


## 11. 과거 수요 특징은 갑작스러운 구조 변화를 늦게 따라감

lag와 rolling 특징은
최근 수요 패턴이 이후에도 어느 정도 이어진다는
가정에서 유용한 특징.

하지만 팬데믹처럼
수요 수준이 갑자기 변하면

과거의 높은 이용량이
한동안 특징에 계속 남아 있게 됨.

따라서 모델이 새로운 수요 수준을
즉시 반영하기 어려움.

### 대응

성능이 떨어졌다고
무조건 특징 개수부터 늘리지 말 것!

먼저 해당 시기에
외부 구조 변화가 있었는지 확인.

필요하다면 구조 변화를 설명할 수 있는
외부 특징을 추가해야 함.


## 12. 모델 점수만으로 원인을 설명할 수 없음

MAE, R² 등의 지표는
모델이 얼마나 잘 예측했는지는 보여주지만

왜 특정 기간에서
성능이 좋아지거나 나빠졌는지까지
설명해 주지는 않음.

### 대응

모델 평가 결과에서 이상한 구간이 발견되면
EDA와 추가 분석으로 원인을 다시 추적.

이번 프로젝트에서는
시간순 검증에서 발견한 2020년 성능 저하를
팬데믹 구조 변화 분석으로 연결.

전체 흐름은 다음과 같음.

```text
모델 평가
    ↓
이상한 성능 구간 발견
    ↓
원본 데이터와 시계열 구조 확인
    ↓
원인 분석
    ↓
특징 및 해석에 반영
```

모델 점수 확인에서 끝내지 않고
왜 그런 결과가 나왔는지까지
데이터에서 다시 확인하는 것이 중요.


## 13. 데이터 범위를 넘어 일반화하면 안 됨

현재 데이터에는
서울·수도권의 여러 철도 노선이 포함되어 있지만
수도권 전철 전체가 포함된 것은 아님.

분석 데이터에 없는 노선까지 포함하여
'수도권 전철 전체의 결과'라고 표현하면
실제 데이터 범위를 넘어선 해석이 됨.

### 대응

분석 결과를 설명할 때
실제 수집 범위를 명확하게 밝힐 것.

데이터의 한계도
분석 결과의 일부로 기록해야 함.


## 14. 실행되는 코드와 올바른 분석은 다름

코드가 오류 없이 실행된다는 것은
프로그램이 동작한다는 의미.

하지만 다음 문제까지
자동으로 보장되는 것은 아님.

- 변수의 의미가 올바른가
- 미래 정보가 섞이지 않았는가
- 데이터 범위를 정확히 이해했는가
- 평가 방식이 실제 사용 환경과 비슷한가
- 구조 변화를 단순 이상치로 처리하지 않았는가

따라서

```text
코드가 실행되는가?
```

와

```text
분석 논리가 올바른가?
```

는 별도로 확인해야 함!


## 15. 최종 체크리스트

새로운 데이터나 모델을 추가할 때
다음 항목을 다시 확인할 것.

```text
[ ] 원본 변수의 의미를 확인했는가
[ ] 역명 등 범주형 값의 표기가 일관적인가
[ ] 결측과 이상값 처리에서 정상 정보를 잃지 않았는가
[ ] 날씨 변수의 정의와 단위를 확인했는가
[ ] 예측 시점에 알 수 없는 정보를 사용하지 않았는가
[ ] 시간 순서를 유지하여 평가했는가
[ ] random split의 점수만 보고 판단하지 않았는가
[ ] fold별 성능을 확인했는가
[ ] 성능 급락 시기의 데이터 구조를 확인했는가
[ ] 외부 구조 변화를 단순 이상치로 처리하지 않았는가
[ ] 분석 결과를 실제 데이터 범위 안에서 해석했는가
```

이번 프로젝트에서 가장 중요하게 확인한 것은

높은 모델 점수만 보는 것이 아니라  
데이터가 만들어진 과정과 실제 예측 시점을 고려하여  
결과가 왜 그렇게 나왔는지까지 검증하는 것!
