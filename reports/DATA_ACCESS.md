
# 데이터 접근 및 수집 기록

## 1. 문서 목적

이 문서는 서울 지하철 수요와 날씨 예측 프로젝트에서
사용한 데이터의 출처와 수집 과정을 기록하고 있음.

분석 결과뿐 아니라
데이터를 어떤 경로로 확보하고 저장했는지,
수집 과정에서 어떤 제약이 있었는지를
재현 가능하도록 남기는 것을 목적으로 함.

또한 데이터 정제 및 SQLite 적재 과정에서 발견한 문제와
검증 결과를 함께 기록하여 분석 결과의 해석 범위를 명확히 함.

## 2. 지하철 데이터

### 데이터 출처 및 수집 방법

지하철 데이터는 서울 열린데이터광장의
`OA-12914` 데이터셋에서 수집함.

- 제공처: 서울 열린데이터광장
- 데이터셋 ID: `OA-12914`
- 다운로드 주소: https://datafile.seoul.go.kr/bigfile/iot/inf/nio_download.do?useCache=false
- 수집 코드: `src/download_data.py`
- 수집 기간: 2019~2024년

연도별 파일 구성은 다음과 같음.

| 기간 | 파일 구성 | 다운로드 seq |
|---|---|---|
| 2019년 | 연도별 CSV 1개 | 110 |
| 2020년 | 연도별 CSV 1개 | 111 |
| 2021년 | 연도별 CSV 1개 | 112 |
| 2022년 | 연도별 CSV 1개 | 113 |
| 2023년 | 월별 CSV 12개 | 114~125 |
| 2024년 | 월별 CSV 12개 | 126~137 |

다운로드는 HTTP POST 요청을 사용하며,
데이터셋 ID와 파일 순번을 전달함.

수집 과정에서는 CSV 필수 컬럼과 날짜 범위를 검증함.

2019~2022년은 연도별 날짜 누락 여부를 확인하고,
2023~2024년은 월별 날짜 및 제목행 일치 여부를 확인한 뒤
12개월 데이터를 연도별 파일로 결합함.

원본 CSV의 인코딩은 `utf-8-sig`, `euc-kr`, `cp949`
순서로 확인하고, 최종 파일은 UTF-8 BOM 형식으로 저장함.

검증에 성공한 경우에만 임시 파일을 최종 파일로 교체함.

최종 저장 파일은 다음과 같음.

`data/raw/subway_daily_2019.csv`부터
`data/raw/subway_daily_2024.csv`까지 총 6개임.

다운로드 주소나 파일 순번은 제공처의 파일 구성 변경에 따라
달라질 수 있으므로 재수집 시 응답 검증이 필요함.

### 데이터 내용

서울·수도권 철도의 일별 역별 승하차 이용량 데이터를 사용.

주요 항목은 다음과 같음.

- 날짜
- 노선
- 역명
- 승차 / 하차 구분
- 이용량

수집한 원본 데이터는
프로젝트 내부에서 일관된 형식으로 변환한 뒤 SQLite 데이터베이스에 적재.

분석에 사용한 기간은 2019년 1월 1일부터
2024년 12월 31일까지임.

원본 지하철 데이터는 1,319,521행이며,
승차·하차별로 분리하면 총 2,639,042행이 됨.

## 3. 날씨 데이터

### 데이터 출처 및 수집 방법

날씨 데이터는 Open-Meteo의 과거 날씨 API에서 수집함.

- 제공처: Open-Meteo
- API: https://archive-api.open-meteo.com/v1/archive
- 수집 코드: `src/collect_weather.py`
- 수집 기간: 2019-01-01 ~ 2024-12-31
- 서울 기준 위도: 37.5714
- 서울 기준 경도: 126.9658
- 시간대: `Asia/Seoul`
- 저장 파일: `data/raw/weather_daily.csv`

서울 종관기상관측소(ASOS 108번)의 위치를
좌표 기준으로 사용했지만, 실제 날씨 데이터 제공처는
기상청 ASOS 관측 자료가 아닌 Open-Meteo임.

API 요청 시 일별 날씨 변수 8개를 지정하고,
응답의 `time` 컬럼을 `date`로 변경하여 저장함.

수집한 데이터는 다음 항목을 검증함.

- 필수 컬럼 존재 여부
- 날짜 형식
- 중복 날짜 여부
- 분석 기간 밖 날짜 여부
- 2019~2024년 전체 2,192일의 날짜 누락 여부
- 날씨 변수의 숫자 형식

네트워크 오류나 응답 검증 실패 시 최대 3회 재시도함.

검증에 성공한 데이터를 임시 CSV로 저장한 뒤
다시 검증하고 최종 파일로 교체함.

날씨 변수별 물리적 허용 범위 검증과
API 데이터 버전 기록은 향후 보완 사항으로 남겨둠.

지하철 이용량과 결합하기 위해 서울의 일별 기상 데이터를 사용.

분석 기간은 2019년 1월 1일부터
2024년 12월 31일까지이며, 총 2,192일임.

주요 날씨 변수는 다음과 같음.

- 평균 기온
- 최고 기온
- 최저 기온
- 총강수량
- 강우량
- 적설량
- 최대 풍속
- 습도

날짜를 기준으로 지하철 일별 데이터와 결합.

날씨 데이터의 수집 및 처리 코드는
`src/collect_weather.py`에서 관리함.

## 4. 총강수량과 강우량

날씨 데이터에서는 총강수량과 실제 강우량을 구분.

```text
precip_mm = 총강수량
rain_mm   = 강우량
```

원본 데이터를 확인한 결과
`precip_mm`과 `rain_mm`이 서로 다른 날짜가 존재함.

총강수량에는 눈과 같은 형태의 강수가 포함될 수 있기 때문.

따라서 비가 지하철 이용량에 미치는 영향을 분석할 때는
총강수량을 그대로 비의 기준으로 사용하지 않고 `rain_mm`을 사용.

강우 여부를 비교하는 분석에서는
`rain_mm >= 1.0`을 기준으로 강우일을 정의함.

강우 강도별 분석에서는 0mm를 기준으로
0~5mm, 5~20mm, 20mm 초과 구간을 별도로 비교함.

두 분석은 강우일 정의가 다르므로
각 집단에 포함되는 날짜 수도 서로 다름.

## 5. SQLite 저장

수집한 데이터를 파일 상태로만 사용하지 않고 SQLite 데이터베이스에 적재.

프로젝트에서 사용하는 데이터베이스는 다음과 같음.

```text
data/seoul_transit.db
```

사용한 주요 테이블은 다음과 같음.

```text
subway_daily
weather_daily
```

`subway_daily`에는 지하철 일별 이용량 데이터를 저장.

`weather_daily`에는 일별 날씨 데이터를 저장.

분석 과정에서는 목적에 따라
DB의 원본형 테이블을 직접 조회하거나,
전처리 파이프라인을 통과한 통합 데이터를 사용.

### 지하철 데이터 적재 결과

| 항목 | 결과 |
|---|---:|
| 원본 지하철 데이터 | 1,319,521행 |
| 승차·하차 분리 후 데이터 | 2,639,042행 |
| 고유 키 중복 초과 행 | 372행 |
| SQLite 적재 결과 | 2,638,670행 |

SQLite 적재 시 고유 키는
`(date, line, station, io_type)`을 사용함.

동일 키의 중복 저장을 방지하기 위해
`INSERT OR IGNORE` 정책을 사용함.

따라서 동일한 키가 여러 번 등장하면
최초로 입력된 행만 저장하고
이후 중복되는 행은 제외됨.

## 6. 원본 데이터와 정제 데이터 구분

분석 목적에 따라 원본형 데이터와 정제 데이터를 구분해서 사용.

일반적인 분석과 모델링에서는 전처리가 완료된 통합 데이터를 사용.

반면 전처리 자체가 왜 필요한지 검증할 때는
이미 정제된 데이터를 다시 확인하면 문제가 사라진 상태이기 때문에 적절하지 않음.

따라서 전처리 검증에서는 SQLite의 원본형 테이블을 직접 조회.

이를 통해 다음 문제를 실제 데이터에서 확인하였음.

- 역명 부기명에 따른 표기 차이
- `total <= 0`인 비정상 이용량
- 총강수량과 강우량의 차이
- 실제 데이터에 포함된 노선 범위

추가로 SQLite 적재 전 원본 데이터를 검사하여
고유 키 중복 및 중복 제외 행의 이용량을 검증함.

## 7. 데이터 결합

지하철과 날씨 데이터는 날짜를 공통 기준으로 결합.

전체 처리 흐름은 다음과 같음.

```text
지하철 원본 데이터                날씨 원본 데이터
        ↓                               ↓
   SQLite 적재                     SQLite 적재
        ↓                               ↓
 지하철 데이터 정제               날씨 데이터 정제
        ↓                               ↓
 일 단위 이용량 집계             일 단위 날씨 데이터
        │                               │
        └───────────┬───────────────────┘
                    ↓
              날짜 기준 결합
                    ↓
              통합 분석 데이터
                    ↓
           달력·팬데믹 특징 추가
                    ↓
           lag / rolling 특징 생성
                    ↓
                모델링
```

통합 데이터에는 이후 요일, 주말, 공휴일, 팬데믹 국면 등의 달력 특징을 추가.

모델링 단계에서는 다시 과거 수요를 이용한 lag 및 rolling 특징을 생성.

lag 및 rolling 특징은 과거 실측 이용량을 사용하므로
과거 수요가 확보되지 않은 임의의 미래 날짜를
독립적으로 예측하는 데에는 추가 설계가 필요함.

## 8. 데이터 접근 시 주의사항

### 역명 표기

같은 역이라도 역명 뒤에 부기명이 붙어 있을 수 있음.

예를 들어 다음과 같은 형태.

```text
강변(동서울터미널)
경복궁(정부서울청사)
광화문(세종문화회관)
```

따라서 역 단위 분석에서는 역명 표준화가 필요.

### 비정상 이용량

이용량이 0 이하인 데이터가 존재.

이 경우 행 전체를 삭제하면
같은 날짜와 역의 다른 정상 정보까지 함께 손실될 수 있음.

따라서 문제 있는 이용량 값만 결측으로 처리하도록 구성.

### 날씨 변수의 의미

`precip_mm`을 단순히 '비의 양'으로 해석하면 안 된다고 판단함.

비 효과를 분석할 때는
실제 변수의 정의를 확인한 뒤 `rain_mm`을 사용해야 함.

### 데이터 커버리지

현재 수집 데이터는 수도권 전철 전체를 완전히 포함하지 않음.

따라서 데이터 범위를 넘어서는 과도한 일반화를 피해야 함.

또한 연도별 관측 역 구성이 달라질 수 있으므로
팬데믹 전후 이용량 비교에서는 고정 역 집합을 이용한
민감도 분석을 추가로 수행함.

2019~2024년 동안 연간 관측률 95% 이상인
노선·역 조합 576개를 고정한 결과,
2024년 이용량은 2019년 대비 7.84% 낮았음.

전체 역 기준 변화율인 -7.22%와 비교해도
완전한 회복에 이르지 못했다는 결론은 유지됨.

### 원본 데이터와 Git 관리

원본 데이터와 SQLite DB는 로컬 `data/` 폴더에서 관리함.

현재 프로젝트의 Git 작업에서는
원본 데이터가 포함된 `data/` 폴더를
커밋 대상에 포함하지 않도록 주의하고 있음.

따라서 GitHub 저장소의 소스 코드만으로
모든 원본 데이터가 확보되었다고 가정하면 안 됨.

재현 시에는 원본 파일을 준비하고
프로젝트의 데이터 수집·검증 절차를 확인해야 함.

데이터 준비와 실행 절차는
프로젝트 루트의 `README.md` 및
`src/download_data.py`, `src/collect_weather.py`를 참고.

## 9. 재현 시 확인할 사항

프로젝트를 다시 실행하거나 새로운 기간의 데이터를 추가할 경우
다음 사항을 우선 확인할 것.

- 데이터의 날짜 범위
- 노선 및 역명 표기 변화
- 결측값과 비정상 이용량
- 지하철 데이터의 중복 여부
- 날씨 변수의 단위와 의미
- 지하철과 날씨 데이터의 날짜 정합성
- 새롭게 추가되거나 누락된 노선
- 기존 전처리 규칙이 새 데이터에도 유효한지

### 원본 데이터 중복 검증 결과

지하철 원본 데이터를 승차·하차별로 분리한
2,639,042행에서 고유 키 중복 초과 행 372행을 확인함.

| 검증 항목 | 결과 |
|---|---:|
| 중복 초과 행 | 372행 |
| 중복 그룹 전체 행 | 744행 |
| 필수 키 결측·공백 행 | 0행 |
| 중복 키 그룹 중 이용량이 다른 그룹 | 372개 |
| 중복 발생 기간 | 2019~2021년 |
| 중복 발생 노선 | 경의선 |
| 제외된 행의 이용량 합계 | 230,226건 |
| 원본 전체 이용량 대비 비율 | 0.000829% |

중복은 경의선의 서울역, 홍대입구,
디지털미디어시티, 공덕에 집중되어 있었음.

중복 그룹은 모두 동일 키에
서로 다른 이용량이 기록된 사례였음.

원본 전체 이용량은 27,773,755,430건이며,
기존 중복 처리 정책을 적용한 뒤
이용량 합계는 27,773,525,204건임.

두 합계의 차이는 230,226건으로,
원본 전체 이용량의 약 0.000829%에 해당함.

다만 이 수치가 실제 누락된 이용량을
의미한다고 단정할 수는 없음.

동일 키에 서로 다른 이용량이 기록된 원인을
원본 데이터만으로 확정할 수 없기 때문임.

따라서 임의로 중복 이용량을 합산하지 않고
기존 `INSERT OR IGNORE` 정책을 유지함.

별도의 빈 SQLite DB를 생성하여
고유 키 개수와 적재 결과가 일치하는 것을 확인함.


### 실행 및 재현성 검증 상태

기존 로컬 환경에서 전체 파이프라인과
`verify_code.py --after-run` 검증을 정상 완료함.

추가로 Python 3.14.6을 사용하는 별도 프로젝트 복사본에서
새 가상환경을 생성하고 `requirements.txt`의 의존성을 설치함.

`pip check` 검사에서 의존성 충돌이 없음을 확인하였으며,
새 가상환경의 Python으로 `run_all.py`를 실행하여
전체 15단계를 정상 완료함.

최종 검증에서는 다음 메시지를 확인함.

```text
[PASS] 프로젝트 소스, 원본 데이터, 실행 산출물이 모두 정상적으로 존재함
```

따라서 기존 개발 환경에만 의존하지 않고
새 가상환경에서도 전체 파이프라인이 실행되는 것을 확인함.

다만 원본 CSV는 기존에 수집한 파일을 복사하여 사용했으므로
외부 데이터 제공처에서 처음부터 다시 다운로드하는 과정까지
재검증한 것은 아님.
